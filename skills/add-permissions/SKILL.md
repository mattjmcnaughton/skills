`/add-permissions <command...>` adds one or more focused permission grants to the current repo so an agent (Claude Code or Codex CLI) can run the listed commands unprompted from now on. It writes to both `.claude/settings.json` (committed) and `.codex/rules/added.rules` (a new sibling file under `.codex/rules/`) for symmetric coverage.

This skill is the **targeted complement** to `/setup-permissions`. It does not detect runners, derive deny scopes, or audit the repo. It appends one or a few entries to existing files and stops.

## When to use which skill

| Skill | Use when |
|---|---|
| `/setup-permissions` | Bootstrapping the repo, or rebuilding the baseline after a runner change. Detects, renders, writes the full managed surface. |
| `/add-permissions` | The agent just got prompted for a single command and you want to persist that grant. One-off, no full rebuild. |
| `/fewer-permission-prompts` | Bulk-promote everything that has been prompted across recent session transcripts. Transcript-driven, not command-driven. |

## Input

Pass one or more commands as arguments:

```
/add-permissions just newtarget
/add-permissions "pnpm run test:watch" "pnpm run build"
```

If no arguments are given, ask the user for the command(s).

For each command, ask **one** question: literal or broad?

```
Command: pnpm run test:watch
  literal — exact match only: `Bash(pnpm run test:watch)`
  broad   — prefix glob: `Bash(pnpm run test:*)` matches any pnpm test script
[literal/broad] (default: literal)
```

Default to **literal**. Broad is opt-in because it's harder to take back and the user often only knows they want this one command, not the whole family.

The literal/broad question only affects Claude — Codex's `prefix_rule` is always prefix-matching, so trailing args pass through regardless.

## What gets written

### `.claude/settings.json`

Append one entry to `permissions.allow`:

- literal: `Bash(<command>)`
- broad: `Bash(<prefix>:*)` where `<prefix>` is the command up to (but not including) the last argument the user wanted to wildcard

Merge rules:

1. Read the existing file. If parse fails, refuse to overwrite — print the path and error, ask the user to fix it manually.
2. Insert the new entry into `permissions.allow`. **Preserve all existing entries**, managed and non-managed alike. This skill is purely additive.
3. Dedup and sort the array alphabetically.
4. Write with 2-space indent and trailing newline.
5. If the file doesn't exist, create it with a minimal `{ "permissions": { "allow": [<entry>] } }` shape.

### `.codex/rules/added.rules`

Append a `prefix_rule(...)` block. The file uses its own managed marker so it stays independent from `/setup-permissions`'s `default.rules`:

```starlark
# managed:add-permissions
# Generated by /add-permissions. Each entry was added on demand to grant a
# specific command unprompted. Hand-authored team rules belong in a sibling
# file (e.g., team.rules) — Codex loads every *.rules in this directory.

prefix_rule(
    pattern = ["just", "newtarget"],
    decision = "allow",
    justification = "Added via /add-permissions.",
)
```

Pattern translation: split the literal command on whitespace and use the tokens as the pattern. Quoted arguments containing spaces stay grouped:

| Input command | Codex pattern |
|---|---|
| `just newtarget` | `["just", "newtarget"]` |
| `pnpm run test:watch` | `["pnpm", "run", "test:watch"]` |
| `git remote add origin <url>` | `["git", "remote", "add", "origin"]` (trailing arg dropped — prefix_rule allows it through automatically) |

Merge rules:

1. If the file doesn't exist, create it with the marker header and the new `prefix_rule`.
2. If it exists **with** the `# managed:add-permissions` marker, parse the existing `prefix_rule` patterns, dedup the new addition against them, append if new, write back with the same header.
3. If it exists **without** the marker, refuse and tell the user: "this file has hand-authored content; rename it (e.g., to `team.rules`) and rerun, or pass `--force` to overwrite". The skill must not silently obliterate hand-authored rules.

### Conflict and safety checks

Before writing, check each addition and surface anything notable:

- **Deny-floor overlap.** If the user is trying to add a `Read(./<glob>)` entry that contradicts the secret-deny floor (`.env`, `*.key`, `secrets/**`, etc.), refuse and tell them why. Bash commands aren't denied by the floor — they only need this check for explicit `Read(...)` additions.
- **Already present.** If the addition is already in `permissions.allow` (Claude) or already matches an existing `prefix_rule` (Codex), say so and skip — no-op.
- **Shell metacharacters.** If the command contains `$`, backticks, redirects, or pipes, warn that Codex's `prefix_rule` cannot match these and the entry will only take effect on the Claude side. Recommend wrapping in a runner target instead.

## Default flow

1. Parse input commands (from arguments or by asking).
2. For each command, ask literal-vs-broad.
3. Run conflict checks; surface warnings or refusals.
4. Show a diff preview: what entries are being added to which files.
5. Ask for confirmation. On accept, write `.claude/settings.json` and `.codex/rules/added.rules` in one pass.
6. Print a final summary line, including the Codex restart reminder.

Always show the diff before writing. Always allow the user to back out.

## Interaction with `/setup-permissions`

`/setup-permissions` preserves non-managed entries in `.claude/settings.json` by default (see that skill's "Claude merge rules"). Entries written here look like non-managed entries to it, and survive subsequent setup-permissions runs.

On the Codex side, `added.rules` is a separate file from `default.rules`. `/setup-permissions` only regenerates `default.rules`, so `added.rules` is untouched across setup-permissions runs.

This means: this skill's additions persist across the full setup-permissions lifecycle. No coordination required between the two skills.

## Restart note

Codex loads `.rules` files at startup. After this skill writes to `.codex/rules/added.rules`, the user must restart Codex CLI for the new rule to take effect. Print a one-line reminder at the end of the run.

## Invocation

```
/add-permissions                                   # ask interactively for the command(s)
/add-permissions just newtarget                    # one literal grant
/add-permissions "pnpm run build" "pnpm run lint"  # multiple grants in one pass
```

## Guidelines

- Plain text only. No emojis in skill output or in written files.
- Single-purpose: this skill only adds. It does not remove, audit, detect, or rebuild.
- Symmetric by default: every grant lands in both Claude and Codex artifacts.
- Idempotent on input: rerunning with the same command is a no-op.
- Never overwrite a file that lacks the expected marker. Refuse and ask.
- Bash-shaped commands only in v1. MCP tool allowlist additions (`mcp__server__tool`) and Read/Glob/Grep scope edits are out of scope; recommend `/setup-permissions` or `/fewer-permission-prompts` for those cases.
