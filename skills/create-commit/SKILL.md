name: create-commit
description: Generate and apply a Conventional Commits message for staged changes (or a specified scope). Use after /review-suite when the changes are ready to land, or during /build for checkpoint commits.
---

Produce a Conventional Commits-formatted message for the requested scope, present it for approval, and commit on confirmation.

## Determine scope

Ask if it isn't clear:
- `staged files` (default if there are staged changes)
- `HEAD` (just-made unstaged + tracked changes; will be staged then committed)
- `last commit` (amend a commit message — only if user explicitly asks)
- `<commit-hash>` (rewrite a specific commit's message)

When called from `/build` for a checkpoint, scope is "staged files for the current step" — `/build` passes the step name/number through.

## Analyze the diff

Inspect with the appropriate command (`git diff --cached`, `git diff HEAD~1 HEAD`, etc.). Identify:
- The primary purpose (feat / fix / refactor / docs / test / chore / etc.).
- A concise scope (`auth`, `parser`, `api`, ...). Omit if the change is broadly applicable.
- The substantive *why* of the change, not just the *what*.

## Issue reference (optional)

If `.agentic/<slug>/ticket.json` exists, derive `Closes #N` (features) or `Fixes #N` (bugs) automatically. Otherwise ask the user once; accept "no".

## Format

```
<type>(<scope>): <subject>

<optional body — bullet points of what & why>

<optional footer: Closes #N / Fixes #N>
```

Rules:
- **Type**: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. For build checkpoints with a failing gate, use `wip` and append `[gate failed]` to the subject.
- **Subject**: imperative ("add", "fix", "rename"), lowercase first letter (unless proper noun), no trailing period, ≤72 chars.
- **Body**: explain *why* via bullets. Skip if the subject is self-evident.
- **No AI attribution.** Never include "generated by AI" or co-author trailers unless the user asked for them.

## Present and execute

1. Show the proposed message in a fenced block.
2. Ask: "Commit with this message? (y/n)"
3. On `y`: run `git commit` (with `-m` or via a HEREDOC for multi-line). Confirm "Commit successful: <sha-short>".
4. On `n`: stop. Don't try again with edits unless asked.

## Guidelines

- Accuracy first. The message must truthfully reflect what changed.
- Avoid scope creep into adjacent code that wasn't actually edited.
- One commit, one logical change. If the staged diff covers two unrelated things, point that out instead of writing one over-broad message.
- Plain text only. No emojis in commit messages.
